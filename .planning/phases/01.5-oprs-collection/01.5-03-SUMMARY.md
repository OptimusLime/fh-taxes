# Phase 01.5 Plan 03: HTML parsers (parse_m4 + parse_sr) Summary

**One-liner:** Two pure-function HTML parsers (`parse_m4`, `parse_sr`) bridge
the OPRS raw cache to canonical D-32/D-33 dicts, validated against 4,222 real
cache files plus 23 unit tests with sanitized real fixtures.

## What was built

### `src/fairhaven_tax/ingest/oprs/__init__.py`
Empty package marker. One-line docstring. Mirrors `src/fairhaven_tax/ingest/sr1a/__init__.py`.

### `src/fairhaven_tax/ingest/oprs/parse_m4.py`
- **`M4_FIELDS`** — 17 canonical keys (D-32 m4 subset): `pams_pin`, `block`,
  `lot`, `qualifier`, `prop_loc`, `square_ft`, `year_built`, `style_code`,
  `bldg_desc`, `land_desc`, `acreage`, `zone`, `map_page`, `class`,
  `current_taxes_1h`, `current_taxes_2h`, `updated_date`.
- **`parse_m4(path: Path) -> dict[str, object]`** — reads file, flattens HTML,
  extracts each field by label-boundary regex, returns dict with every key
  present (None for missing).
- **`extract_ssis(html_text) -> list[str]`** — reuses the collector's
  `sr.cgi?...ssi=N` regex. Dedupes, preserves document order.
- **Coercers**: `_to_decimal` (handles `$`, `,`, `N/A`), `_to_int`
  (zero → None), `_to_date_mdy` (handles `MM/DD/YY` and `MM/DD/YYYY`,
  applying NJ 2-digit-year rule: `<50 → 20xx`, `≥50 → 19xx`).
- **`_flatten`** handles `&nbsp` and `&amp` *with or without* trailing
  semicolon — important OPRS quirk found during testing.

### `src/fairhaven_tax/ingest/oprs/parse_sr.py`
- **`SR_FIELDS`** — 11 canonical keys (D-33): `parcel_pin`, `sale_date`,
  `serial_number`, `grantor`, `grantee`, `sale_price`, `family_sale_flag`,
  `sales_ratio_assessor`, `remarks`, `additional_blocks_lots`, `nu_code`.
- **`parse_sr(path: Path) -> dict[str, object] | None`** — returns None for
  (a) files <100 bytes (`.no_sale` markers, D-23) and (b) empty-template
  responses where the flat text contains the ` // // ` date placeholder.
- **`_is_empty_sr_template(flat) -> bool`** — exposed helper, mirrors
  `datasets/collect_oprs.py:_is_empty_sr_template`.

## Field-extraction regex patterns

### parse_m4 — label-anchored extraction

The m4 page is a series of `<td>label</td><td>value</td>` pairs across
several tables. After flatten the text becomes label/value runs:

```text
Block: 30 Prop Loc: 646 RIVER RD Owner: ... Square Ft: 1763
Lot: 1 District: 1314 FAIR HAVEN ... Year Built: 1912
Qual:  Class: 2 City State: ... Style: 5
...
Updated: 10/09/23 Tax Codes: ... Class4Cd: 0 Desc:
Zone: R-5 Map Page: 6 Acreage: 0 Taxes: 11543.00 / 0.00
```

Single extractor: `_extract(flat, label)` runs

```python
rf"\b{label}:\s*(.*?)(?=\s*(?:LABEL_ALT):|$)"
```

where `LABEL_ALT` is the OR'd list of all known m4 labels. The lazy `(.*?)`
plus zero-or-more whitespace lookahead ensures empty values terminate
correctly (e.g. `Qual:  Class: 2` → `Qual` value is empty, not `Class: 2`).

**Special-case `_extract_taxes`** — the `Taxes:` label is followed by the
`Sale Information` section header which has no colon, so the generic
label-boundary lookahead doesn't terminate. Instead we match the numeric
pair directly:

```python
r"\$?\s*([\d,]+(?:\.\d+)?)\s*/\s*\$?\s*([\d,]+(?:\.\d+)?)"
```

### parse_sr — header-anchored extraction

The sr page is a positional sequence of header rows + data rows:

| Header pattern (post-flatten) | Captures |
| --- | --- |
| `BOOK PAGE DEED DATE DATE RECORDED R.T. FEE PRICE` | book, page, deed_date, date_recorded, rt_fee, sale_price |
| `G R A N T O R ... G R A N T E E` | grantor block (name + address) |
| `G R A N T E E ... TAX MAP` | grantee block |
| `BLOCK X CLASS Y LOT Z CL. 4 TYPE [t] QUAL [q] CONDO C` | block, class, lot, qual, condo |
| `REMARKS: RATIO: <text> <num>` | remarks, sales_ratio |
| `NONUSABLE CODE SERIAL NO. <nu> <serial>` OR `... <serial>` only | nu_code, serial_number |

The NU/Serial regex captures one **or** two trailing tokens. When only one
token is present (NU is blank), length-based disambiguation routes it to
serial (≥4 digits) vs. NU code (1-2 digits).

`family_sale_flag` derives from NU code 07 (NJ DOT "related parties") with
forward-compat support for an explicit "Family Sale: Y/YES" anywhere in
the flat text.

## Deviations from D-32 / D-33 schema

None on field membership. Two clarifications worth documenting:

1. **`additional_blocks_lots`** is typed `list[str] | None`. Returns `None`
   (not empty list) when no additional parcels are recorded, since every
   Fair Haven sample observed has all blank additional rows. The defensive
   tokenizer is in place for forward-compat.

2. **`family_sale_flag`** is `bool` (never None). Defaults to `False` when
   no signal is present. NJ DOT NU code 07 is the canonical source; the
   plan's regex example `Family Sale:?\s+(Y|N|YES|NO)` is supported but
   not present in the OPRS sr.html template.

## Deviations from plan execution

**None.** Plan executed exactly as written. Two minor implementation
notes (Rule 1 self-fixes during GREEN phase, both within the same task):

- Initial `_flatten` regex `&nbsp;|&amp;` did not strip `&nbsp` / `&amp`
  *without* the trailing semicolon. OPRS templates omit the semicolon in
  practice (HTML4 quirk). Fixed: `&nbsp;?|&amp;?`.
- Initial `_extract` lookahead required `\s+` before the next label, which
  caused empty values (e.g. blank `Qual:`) to swallow the next label cell
  (e.g. `Class: 2`). Fixed: lookahead now uses `\s*` so empty values
  terminate immediately.
- `_extract_taxes` upgraded from `split('/')` to a numeric-pair regex
  because the sentinel "Sale Information" has no colon and the
  label-boundary mechanism cannot anchor on it.
- `_NU_SERIAL_RE` upgraded from `(\S+)\s+(\d+)` to `(\S+)(?:\s+(\d+))?`
  with length-based disambiguation, so blank-NU rows (which collapse to
  one token after flatten) extract the serial correctly.

These were caught by test failures and the smoke test against real cache
files; no test changes were needed beyond the originally written set.
