<objective>
Run the comprehensive OPRS collection across all 2,061 class-2 Fair Haven parcels. This is operator-driven work (not autonomous): the operator runs `datasets/collect_oprs.py --mode comprehensive --batch 500` repeatedly, swaps VPN exit between batches, and monitors the rolling error rate. The collector itself is idempotent and resumable; this plan documents the protocol and provides verification queries the operator can run between batches.

Purpose: Populate the cache that PLANs 03/04/05 parse. Without this, all downstream parquet aggregation has nothing to read.

Output: Fully populated `data/raw/oprs_prc/` cache + operator collection log.

This plan has explicit human-action checkpoints because:
1. VPN exit-IP rotation must be performed by a human (no CLI/API for our VPN).
2. Auto-abort triggers require human judgment (continue from new IP vs. wait vs. give up).
3. Final completeness verification is a sanity check before parsers run.
</objective>

  <how-to-verify>
    Loop protocol (operator runs this manually):

    1. Connect VPN to fresh exit IP.
    2. Run a batch:
       ```
       cd /Users/paul/coding/fairhaven/tax_assessment
       uv run python datasets/collect_oprs.py \
         --mode comprehensive \
         --batch 500 \
         --rate 2.0 \
         --jitter-pct 0.50 \
         --max-error-rate 0.10 \
         --error-window 50
       ```
    3. Append a row to `01.5-02-COLLECTION-LOG.md` "Batch Run Log" with: batch number, start/end timestamps, VPN exit (e.g., "exit-7"), requests/ok/no_sale/fail counts from the script's final summary line, aborted (yes/no), brief notes.
    4. If the run aborted with "error rate ... exceeds threshold": disconnect VPN, wait 60s, connect to a DIFFERENT exit IP, re-run.
    5. If 5 consecutive batches abort: pause and investigate (rate limit harder, check User-Agent, verify endpoints not changed). Document in log.
    6. Between batches, run `uv run python datasets/collect_oprs.py --status --mode comprehensive` to verify progress.
    7. Repeat steps 1-6 until status reports `parcels fully complete: 2061` and `sr pending: 0`.

    Expected scale: ~20,000-25,000 requests total. At batch=500 with 2 req/s = ~4 min/batch network time. ~40-50 batches. Multiple sessions over multiple days is normal and expected.

    Stopping conditions:
    - SUCCESS: --status reports 100% complete (2061 parcels fully cached for comprehensive mode + all PDFs).
    - PARTIAL: If after 60+ batches some parcels are stubbornly failing (likely OPRS-side data corruption for those specific block/lots), document the residual list in the log and proceed — Task 3 will reconcile.
